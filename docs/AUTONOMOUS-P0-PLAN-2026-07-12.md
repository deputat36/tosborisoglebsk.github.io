# Автономный план P0 для портала ТОС БГО

Дата: 12 июля 2026 года.

Основание:

- `docs/PORTAL-USER-LEGAL-STRATEGY-AUDIT-2026-07-12.md`;
- issue #205;
- текущие отчёты `data/site_health.json` и `data/content_origin_report.json`.

## Цель

Без участия пользователя закрыть все задачи P0, которые не требуют:

- получения новых персональных данных;
- отправки сообщений председателям или администрации;
- подтверждения официальных документов внешним органом;
- юридического заключения профильного специалиста;
- загрузки фотографий, логотипов или закрытых доказательств.

## Принципы автономной работы

1. Не выдумывать сведения о ТОСах, председателях, контактах, границах, проектах и результатах.
2. Не переводить записи и карточки в `verified` без проверяемого источника.
3. Не создавать новые публичные разделы до закрытия P0.
4. Не хранить согласия, переписку и персональные доказательства в публичном GitHub.
5. Каждое изменение проводить через отдельную ветку, PR и полный CI.
6. Предпочитать небольшие обратимые изменения с автоматической защитой от регрессий.

## Этап A. Остановить искусственный рост публичного контента

Статус: `in_progress`.

Автономные действия:

- удалить из автоматического workflow генерацию стартовых новостей;
- удалить из автоматического workflow генерацию стартовых проектов и потребностей;
- удалить из автоматического workflow генерацию стартовых историй результата;
- сохранить существующие записи, но не создавать новые автоматически;
- добавить аудит, запрещающий возврат этих шагов в основной workflow.

Критерий готовности:

- основной pipeline больше не создаёт новый стартовый публичный контент;
- существующая классификация `verified/editorial/starter/request` сохраняется;
- CI блокирует повторное включение генераторов.

## Этап B. Честный статус рабочей версии

Статус: `in_progress`.

Автономные действия:

- добавить единый заметный статус на ключевые публичные страницы;
- сообщить, что полнота каталога и актуальность сведений проверяются;
- дать ссылки на состояние каталога, источники и форму исправления;
- убрать с главной формулировки, которые обещают подтверждённые реальные истории при отсутствии `verified`-результатов;
- добавить аудит наличия статуса на ключевых страницах.

Ключевые страницы:

- `/`;
- `/tos/`;
- `/residents/`;
- `/partners/`;
- `/projects/`;
- `/needs/`;
- `/done/`;
- `/calendar/`;
- `/documents/`;
- `/legal/`;
- `/create-tos/`;
- `/contacts/`.

## Этап C. Безопасная маркировка муниципальной правовой базы

Статус: `in_progress`.

Автономные действия:

- убрать у локальной копии Устава БГО статус, похожий на подтверждение действующей редакции;
- обозначить файл как локальную копию редакции 2024 года, требующую официальной сверки;
- добавить поля юридической применимости к реестру документов без фиктивного заполнения источников;
- запретить CI использовать слово `действующий` для муниципального документа без официального URL, даты проверки и статуса проверки.

Критерий готовности:

- локальная копия не выглядит гарантированно актуальной;
- правовой раздел сохраняет методическую пользу;
- официальный статус не присваивается автоматически.

## Этап D. Контроль публичной поверхности

Статус: `planned`.

Автономные действия:

- зафиксировать baseline существующих публичных маршрутов;
- запретить появление новой индексируемой страницы без записи в реестре и объяснения пользовательской задачи;
- разрешить генерацию детальных страниц только из существующих структурированных коллекций;
- добавить исключение только через явный review-флаг.

Критерий готовности:

- случайное добавление нового публичного раздела блокирует CI;
- служебные страницы обязаны иметь `noindex`;
- новая публичная страница требует владельца, аудиторию и сценарий использования.

## Этап E. Метаданные доверия для карточек

Статус: `planned`.

Автономные действия:

- подготовить схему полей `source_type`, `source_ref`, `checked_at`, `checked_by`, `recheck_after`, `verification_scope`, `publication_consent_ref`;
- добавить миграцию с пустыми значениями без изменения статусов;
- обновить валидатор;
- показывать пользователю дату и объём проверки только при наличии данных;
- не считать `source_updated` подтверждением актуальности.

Критерий готовности:

- схема готова к заполнению после получения подтверждений;
- существующие карточки не получают фиктивные источники;
- CI различает техническое обновление файла и реальную проверку сведений.

## Этап F. Юридическая матрица и статусы шаблонов

Статус: `planned`.

Автономные действия:

- создать пустую юридическую матрицу вопросов и источников;
- определить статусы `draft_methodical`, `reviewed_for_current_federal_law`, `reviewed_for_bgo_procedure`, `approved_sample`, `archival`;
- мигрировать рабочие шаблоны в `draft_methodical`, если нет подтверждения иного статуса;
- добавить дату последней юридической проверки и срок повторной проверки;
- добавить аудит, запрещающий `approved_sample` без источника и проверяющего.

Ограничение:

Самостоятельно нельзя переводить документ в `reviewed_for_bgo_procedure` или `approved_sample`.

## Этап G. Публичная и закрытая модель персональных данных

Статус: `planned`.

Автономные действия:

- подготовить структуру будущей политики оператора с незаполненными юридическими реквизитами;
- создать техническую схему ссылок `consent_ref` без хранения согласий в GitHub;
- добавить audit-запрет на файлы и поля, похожие на сканы, подписи, паспорта, банковские реквизиты и закрытые списки;
- описать требования к закрытому хранилищу;
- подготовить черновые шаблоны для последующей юридической проверки с явной меткой `НЕ ИСПОЛЬЗОВАТЬ ДО ПРОВЕРКИ`.

Ограничение:

Нельзя публиковать документ как действующую политику или согласие без определения оператора и юридической проверки.

## Этап H. Упрощение публичной оболочки

Статус: `planned_after_P0_guardrails`.

Автономные действия:

- сократить главное меню до 6–7 пользовательских разделов;
- оставить редакционные инструменты только в `/workbench/`;
- убрать пустую карту из основных CTA;
- заменить витринные блоки неподтверждённых результатов на состояние каталога и запросы сведений;
- сохранить старые URL и не вводить редиректы без проверки.

## Задачи, которые заблокированы без внешнего участия

Нельзя выполнить автономно:

- получить официальный полный реестр ТОСов;
- подтвердить председателей, телефоны, email и границы;
- получить действующий официальный Устав БГО;
- подтвердить муниципальный порядок создания и регистрации ТОС;
- определить оператора персональных данных;
- утвердить политику и формы согласий;
- получить права на реальные фотографии и логотипы;
- провести живые пользовательские тесты с реальными жителями и председателями;
- отправить подготовленные запросы от имени портала без отдельного разрешения.

## Порядок выполнения

1. Этапы A–C одним безопасным P0-пакетом.
2. Этап D отдельным PR.
3. Этап E отдельным PR с миграцией схемы.
4. Этап F отдельным PR.
5. Этап G только как техническая подготовка, без публикации юридических документов как действующих.
6. Этап H после прохождения всех проверок и фиксации публичного baseline.
