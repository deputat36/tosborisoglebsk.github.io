# Governance ручных блокеров

## Назначение

`data/github_manual_tasks.csv` и `/github-tasks/` показывают только те задачи, которые требуют внешнего действия, официального источника, ручной проверки или решения пользователя.

Реестр не обращается к GitHub API во время CI и не считается автоматической копией Issues. GitHub Issues остаются первичным источником фактического статуса, а локальный снимок обновляется отдельным проверяемым PR.

## Текущий набор

В локальном реестре закреплены открытые issues #34, #164, #166, #205 и #254, а также служебная строка `0` для `data/user_decision_queue.csv`.

Закрытая issue #165 не является открытым блокером и не должна возвращаться в CSV или карточки `/github-tasks/`. Требование visual comparison сохраняется как общее правило сопровождения, но больше не связывается с открытой issue #165.

## Канонические источники

Динамические счётчики страницы читают пять локальных источников:

- #34 — `data/verification_readiness_matrix.csv`, 4 карточки;
- #164 — `data/github_pages_manual_check_template.csv`, 8 пунктов;
- #166 — `data/outreach_register.csv`, 15 активных задач;
- #205 — `data/personal_data_decision_packet.csv`, 8 решений;
- #254 — `data/publication_basis_confirmation_register.csv`, 24 карточки.

Ожидаемые размеры сводки: `4 / 8 / 15 / 8 / 24`. Изменение размера требует отдельного осознанного обновления контракта, а не молчаливого изменения HTML.

## Контракт данных

Для каждой строки `github_manual_tasks.csv` обязательны:

- уникальный `issue_number`;
- точное название актуальной задачи;
- поддерживаемая группа и статус;
- существующий локальный инструмент;
- существующий CSV или JSON-источник;
- проверяемый критерий завершения;
- конкретное следующее действие;
- дата актуализации.

Для issues #34, #164, #166, #205 и #254 статус должен оставаться `open`, пока соответствующая GitHub Issue реально не закрыта.

## Контракт страницы

Каждая открытая issue представлена ровно одной карточкой с атрибутом `data-manual-issue`. Порядок карточек фиксирован: 34, 164, 166, 205, 254.

`assets/js/manual-blocker-summary.js` содержит чистые агрегаторы для браузера и Node.js. `assets/js/github-tasks.js` загружает источники через `Promise.allSettled`, обновляет карточки и показывает ошибку отдельно для недоступного файла.

Страница должна честно отражать границы:

- public smoke не заменяет ручную проверку Settings → Pages;
- подготовленный запрос не считается отправленным;
- технический audit не создаёт официальный источник;
- обычный ответ не создаёт согласие на распространение;
- режим `pre_legal_readiness` сохраняется до отдельного решения;
- динамический счётчик не изменяет исходный CSV и не закрывает GitHub Issue.

## Расчёт прогресса

- #34: количество карточек, допускающих подтверждённый статус, и сумма принятых обязательных элементов;
- #164: количество реально заполненных пунктов ручной проверки;
- #166: активные, готовые, отправленные, завершённые и просроченные запросы;
- #205: назначенные роли, готовность к проверке, утверждение и реализация восьми решений;
- #254: готовность к отправке, отправка, ответы и завершённый редакционный разбор.

Счётчики используют существующие валидаторы outreach, publication basis и personal data decision packet. Контактные данные, сырые ответы и закрытые доказательства в агрегаты не попадают.

## CI

`scripts/audit_github_manual_tasks.js` проверяет CSV, страницу, пять источников, ожидаемые размеры, npm-команды, project-mode, документацию и read-only workflow.

`scripts/test_github_manual_tasks.js` доказывает отрицательные сценарии:

- возвращение закрытой issue #165;
- потеря обязательной issue #205;
- возврат устаревшего объяснения #164;
- удаление строки очереди решений;
- потеря одной из четырёх приоритетных карточек;
- фиктивный `sent` без обязательных полей.

`.github/workflows/manual-tasks-governance.yml` работает в режиме read-only и не изменяет Issues, CSV или HTML. При каждом запуске он сохраняет короткие `test.log` и `audit.log` в artifact `manual-tasks-diagnostics` для разбора сбоев.

## Порядок обновления

1. Проверить фактическое состояние GitHub Issue.
2. Изменить соответствующий канонический журнал после реального действия.
3. При изменении состава блокеров обновить `github_manual_tasks.csv` и очередь решений.
4. Запустить self-test, audit и full project-mode.
5. Зафиксировать результат небольшим PR.

Нельзя закрывать внешний блокер только потому, что обновлена служебная страница, создан шаблон или появился зелёный технический audit.
