# Visual capture для портала ТОС БГО

Дата: 13 июля 2026 года.

## Назначение

Этот пакет добавляет воспроизводимый браузерный захват 14 контрольных сценариев из `data/css_regression_matrix.csv`.

На данном этапе инструмент:

- не изменяет CSS;
- не изменяет HTML и данные сайта;
- не сохраняет PNG в репозиторий;
- не объявляет снимки утверждённым baseline;
- не сравнивает кадры со старыми файлами из draft PR №220;
- создаёт только временный GitHub Actions artifact для проверки актуальной основной ветки.

## Workflow

Файл: `.github/workflows/visual-capture.yml`.

Права workflow ограничены:

```yaml
permissions:
  contents: read
```

Workflow:

1. проверяет синтаксис capture-скрипта;
2. устанавливает Chromium через Playwright;
3. поднимает локальный статический сервер;
4. выполняет 14 сценариев матрицы;
5. формирует PNG, `manifest.json`, `README.md` и серверный лог;
6. загружает результат как Actions artifact на 30 дней;
7. останавливает локальный сервер.

Workflow не делает commit, push и не использует токены для записи.

## Что проверяет capture

Для каждого сценария фиксируются:

- маршрут;
- viewport;
- тема;
- действие пользователя;
- экранный или печатный режим;
- PNG и его SHA-256;
- ширина документа и наличие horizontal overflow;
- состояние мобильного меню;
- фактическая тема документа;
- ошибки JavaScript;
- ошибки страницы;
- failed requests.

## Режим первого запуска

Первый запуск выполняется с:

```text
VISUAL_CAPTURE_ENFORCE_QUALITY=false
```

Это означает:

- runtime-сбой, отсутствующий маршрут или неполный набор снимков блокирует workflow;
- визуальные и браузерные замечания не скрываются, а записываются в `quality_failures` manifest;
- наличие замечаний не блокирует capture-only пакет до ручного просмотра доказательств.

Такой режим нужен, чтобы сначала зафиксировать реальное состояние актуальной основной ветки, а не автоматически переносить выводы из разошедшегося draft PR №220.

## Порядок дальнейшей работы

1. Запустить workflow на чистой ветке от актуального `release-2025-12-22`.
2. Скачать artifact и проверить все 14 PNG.
3. Разобрать `manifest.json` и каждое `quality_failure`.
4. Не утверждать baseline при runtime failures, пропущенных кадрах или необъяснённых проблемах.
5. Исправлять реальные CSS/HTML-дефекты отдельным небольшим PR.
6. Повторить capture после исправлений.
7. Только после визуального review сохранить утверждённые PNG и manifest отдельным коммитом.
8. Затем добавить pixel comparator и включить блокирующий quality gate.

## Критерий готовности capture-пакета

- workflow запускается на актуальной основной ветке;
- получено 14 из 14 PNG;
- `failures` в manifest пуст;
- artifact содержит manifest, README и серверный лог;
- все quality findings перечислены явно;
- в пакете отсутствуют CSS-изменения и утверждённые baseline-файлы.
