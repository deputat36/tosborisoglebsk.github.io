# Управление статусным документом

## Назначение

`docs/STATUS.md` — человекочитаемый снимок основной ветки. Он не должен вручную дублировать устаревшие цифры из generated-отчётов и не должен выдавать закрытые или черновые ветки за фактическое состояние production-кода.

## Источники метрик

Автоматически сверяются:

- `data/site_health.json` — страницы, каталог, SEO, ссылки и итоговая оценка;
- `data/accessibility_performance_report.json` — расширенная область обхода и бюджеты ресурсов;
- `data/content_origin_report.json` — распределение материалов по происхождению;
- `data/personal_data_readiness.json` — режим портала и количество незавершённых юридических решений.

## Детерминированный updater

`scripts/update_status_document_metrics.js` изменяет только заранее определённые строки:

- дату обновления;
- числовые показатели раздела «Актуальные метрики основной ветки»;
- распределение `content_origin`;
- режим `personal_data_readiness`;
- число обязательных юридических решений, пока все они имеют статус `pending`.

Updater не меняет:

- выводы;
- приоритеты;
- список активных задач;
- юридические формулировки;
- статусы отправки или получения ответов;
- сведения о карточках ТОС;
- ссылки на evidence;
- решения о публикации.

Если юридические решения перестанут быть полностью `pending`, updater блокируется и требует отдельного редакционного изменения документа.

## Блокирующий audit

`scripts/audit_status_document.js` проверяет:

- основную ветку `release-2025-12-22`;
- закрытый без слияния статус PR #220;
- отсутствие claims о «рабочем draft PR #220»;
- точные метрики `site_health`;
- точные показатели accessibility/performance;
- нулевые SEO, link, technical и budget findings;
- согласованность public count между двумя независимыми отчётами;
- актуальные totals `content_origin`;
- режим `pre_legal_readiness` и восемь pending-решений.

## Self-test

Два self-test доказывают:

- корректный документ проходит;
- устаревшее число runtime-ресурсов блокируется;
- возврат claim «Рабочий draft PR: #220» блокируется;
- рассогласование public count между JSON-источниками блокируется;
- updater исправляет известные метрики;
- повторный запуск updater’а идемпотентен;
- неоднозначная структура документа блокируется.

## CI

Проверки подключены к:

- `npm run audit:all`;
- обычному project-mode;
- полному project-mode;
- основному `Generate TOS pages` после формирования итоговых отчётов;
- отдельному read-only workflow `Audit status document`.

Профильный workflow пересобирает метрики в runner и требует нулевой diff `docs/STATUS.md`. Это гарантирует, что сохранённый документ уже соответствует текущим отчётам.

## Границы

- updater не создаёт новые публичные факты;
- внешние задачи не отмечаются выполненными;
- закрытые источники и персональные данные не добавляются;
- GitHub Pages deployment не считается подтверждённым без ручной проверки issue #164;
- обычная переписка не считается юридическим согласием;
- изменение структуры `docs/STATUS.md` требует обновления self-test и отдельного review.
