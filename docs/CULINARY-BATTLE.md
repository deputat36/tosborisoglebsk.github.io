# Кулинарный батл ТОС БГО — эксплуатация без административной панели

Статус: **рабочая реализация в отдельной ветке**, НЕ запущена. Не публиковать и не открывать реальные задания без перечисленных ниже проверок.

## Архитектура

- Публичный frontend: `/culinary-battle/` в основном GitHub Pages; общий `site.js`, логотип, темы, глобальные CSS-переменные.
- Edge Function: `supabase/functions/culinary-battle/index.ts` на **отдельном Supabase-проекте**, `verify_jwt=false`: единственная браузерная точка входа, защищённая кодами участников.
- PostgreSQL: `supabase/migrations/20261106140000_culinary_battle.sql`. Таблицы содержат события, команды, блюда, назначения, журнал действий и ограничения частоты.
- Не создавать админку на сайте. Организатор выполняет изменения защищёнными инструментами ChatGPT через GitHub и Supabase.
- В публичном коде НЕТ: кодов участников, перечня назначений, ключа service_role, `BATTLE_PEPPER`. URL Edge Function не секрет.

## Требуется до настройки реального мероприятия

1. Получить от организатора **утверждённые** 18 названий ТОС и 18 названий блюд. Не брать произвольные 18 из каталога 24 ТОСов.
2. Создать отдельный Supabase-проект после уточнения стоимости и согласия пользователя. Не использовать действующие CRM-проекты.
3. Применить миграцию в новый проект и проверить запреты RLS/GRANT и security advisors.
4. Сгенерировать стойкий случайный `BATTLE_PEPPER` (32+ непредсказуемых символа) и надёжно сохранить **вне Git**. Установить один и тот же секрет в защищённом окружении Edge Function и при подготовке кодов. При потере секретного ключа коды перестанут работать.
5. Вне репозитория подготовить UTF-8 `teams.txt` с 18 строками `Название ТОС|tos_slug` (slug опционален) и `dishes.txt` с 18 названиями. В коде и публичных файлах эти данные не хранить как «утверждённые», пока их не подтвердили.
6. Запустить скрипт с `BATTLE_PEPPER` в переменной окружения:

```bash
node scripts/prepare_culinary_battle.mjs \
  --teams /secure/teams.txt \
  --dishes /secure/dishes.txt \
  --output /secure/battle-2026 \
  --slug culinary-battle-2026
```

Папка `--output` должна находиться **вне публичного Git-репозитория**, быть недоступной посторонним и ещё не содержать целевые файлы. Создаются `seed-private.sql` (одноразовый импорт), `codes-private.csv` (персональные коды), `assignments-private.csv` (полная таблица для организатора). Скрипт не выводит коды в терминал. Импорт `seed-private.sql` выполняется защищённым подключением к новому проекту в одной транзакции: после успешного выполнения событие получает статус `ready`, а распределение становится неизменяемым. SQL-импорт никогда не коммитить в Git.

7. Развернуть Edge Function `culinary-battle` с `verify_jwt=false`; это необходимо, потому что посетители не входят в Supabase Auth. Защита реализована уникальным кодом, проверкой HMAC, ограничениями запросов, закрытыми таблицами и Origin. Обязательные секреты: `SUPABASE_URL` (выдаётся платформой), `SUPABASE_SERVICE_ROLE_KEY` (только на сервере), `BATTLE_PEPPER`, `BATTLE_ALLOWED_ORIGIN=https://tosborisoglebsk.ru`. Содержимое секретов никогда не записывать в логи, документы и GitHub.
8. После проверки API установить публичный адрес функции в константу `API_ENDPOINT` файла `assets/js/culinary-battle.js`. Пока она пустая, форма корректно сообщает «Жеребьёвка готовится» и НЕ предлагает тестовых результатов.
9. Перед запуском протестировать браузер на телефоне и ПК, а API — на синтетическом мероприятии в том же **выделенном тестовом окружении** или в отдельном тестовом проекте, не трогая реальный event. После проверки закрыть и удалить синтетическое мероприятие (через защищённые технические действия).
10. Выполнить `update public.battle_events set status='open' where slug='culinary-battle-2026' and status='ready'` через защищённое подключение **только по решению организатора**, после тестов и рассылки кодов.

## Серверный контракт

`GET /functions/v1/culinary-battle?event=culinary-battle-2026`: только `{status, teams: [{id,name}]}`, без назначений и кодов. До `ready` список пуст.

`POST /functions/v1/culinary-battle`: JSON `{event, team_id, code}`; после проверки возвращает только `{team_name, dish_name, revealed_at, first_open}` **для данной команды**. При закрытом событии новым участникам возвращается `closed`, а ранее открывшие получают прежнее блюдо. Повторное нажатие и смена устройства не меняют результат. Ответы помечаются `Cache-Control: private, no-store`.

Разрешены переходы: `draft→ready→open→closed→published` (также `ready→closed` для отмены). После `ready` список и распределение заблокированы триггерами. Перевыпуск кода возможен через защищённую замену только `battle_teams.code_digest`; такой факт автоматически пишется в `battle_actions`. Изменение уже раскрытого назначения **не предусмотрено обычными командами**.

Для полной публикации результатов после статуса `published` требуется отдельное явное решение организатора и проверка страницы публикации: текущий публичный API **не выдаёт полную таблицу**.

## Контроль организатора (только защищённое SQL-подключение)

```sql
select e.slug, e.status,
 count(a.*) as total, count(a.revealed_at) as revealed
from public.battle_events e
join public.battle_assignments a on a.event_id = e.id
where e.slug = 'culinary-battle-2026'
group by e.slug,e.status;

-- Строго закрытый запрос для организатора:
select t.name as tos, d.title as dish, a.revealed_at
from public.battle_assignments a
join public.battle_teams t on t.event_id=a.event_id and t.id=a.team_id
join public.battle_dishes d on d.event_id=a.event_id and d.id=a.dish_id
join public.battle_events e on e.id=a.event_id
where e.slug='culinary-battle-2026'
order by t.name;
```

`status='closed'` запрещает новые раскрытия, но не повторный просмотр по тому же коду. Журнал хранит события `revealed`, `viewed`, `invalid_code`, `rate_limited`, `blocked`, `code_rotated`, `state_changed`; исходные IP, коды и другие личные данные в нём отсутствуют.

## Ограничения

- GitHub Pages не выполняет серверный код. Пока нет выделенного проекта Supabase и реальных списков, страница остаётся в безопасном режиме подготовки.
- Статус `published` означает разрешение организатора на публикацию, но сам по себе не добавляет публичный список: случайного раскрытия назначений не происходит.
- Дополнительная защита от распределённого автоматического перебора (WAF / edge quota) проверяется перед запуском; БД уже ограничивает запросы по клиентскому HMAC-отпечатку и выбранному ТОСу.
