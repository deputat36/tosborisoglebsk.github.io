## Пилот только для ТОС «Уютный» — 12 ноября 2026 года

- По решению организатора **сначала запускается настоящая жеребьёвка только для ТОС «Уютный»**, а не для всех 26 сразу. Первое успешно вытянутое им блюдо расходует **одно из 19** и закрепляется навсегда. Для остальных 25 ТОСов выдача закрыта, даже если их действительные коды уже известны. Повторный просмотр результата «Уютного» по его коду не расходует второе блюдо.
- В новой схеме SQL есть статус `pilot` и поле `pilot_tos_slug`; разрешён переход `draft→ready→pilot→open→closed`. Во время `pilot` `public.battle_reveal` атомарно возвращает `pilot_only` при попытке получить задание любой командой, кроме `uyutnyy`. Действительные код и команда проверяются **перед** сообщением об ограничении.
- GET Edge Function возвращает публичные `status:pilot` и `pilot_team_slug:uyutnyy`; браузер показывает в выпадающем списке только «Уютный». После смены статуса на `open` появятся все 26 ТОСов, а 18 ещё свободных блюд распределятся по очереди первых успешных запросов.
- Начинать пилот **только после успешного облачного тестирования, загрузки текущего приватного seed без повторной генерации кодов, настройки сервера и подтверждения нулевого числа назначений**:
```sql
update public.battle_events
set status='pilot', pilot_tos_slug='uyutnyy'
where slug='culinary-battle-2026' and status='ready';
```
- Открывать участие остальным **только по отдельному подтверждению владельца после проверки «Уютного»**, командой:
```sql
update public.battle_events
set status='open', pilot_tos_slug=null
where slug='culinary-battle-2026' and status='pilot';
```
- Подтверждение блокера: **создать третий бесплатный Supabase-проект в организации «Lider» не удалось**. Управляющий API сообщил об исчерпании двух активных Free-проектов у владельца `deputat36`. Цена добавления проекта API была показана как 0 в месяц, но квота активных бесплатных проектов препятствует созданию. Пауза `lider-bsk-staging` или любого другого существующего CRM-проекта **недопустима без явного согласия владельца**; два CRM-проекта не менялись.
- До решения по отдельному хостингу/тарифу **публичный API пуст, действительная жеребьёвка не запущена**. Секреты и индивидуальные коды не должны попадать в репозиторий или браузер. Всё это отличать от успешно пройденных проверок локального PostgreSQL/Chromium.

Однако **отдельный проект Supabase не создан**, ни миграция, ни закрытый seed, ни функция не развёрнуты, а публичная страница не имеет URL API. Заявлять реальную жеребьёвку работающей нельзя.

Пока `content` пуст, обычная страница закрыта и доступна только локальная демонстрация по `?demo=1`. После размещения **проверенного URL Edge Function** в `content` клиент автоматически блокирует деморежим даже при `?demo=1`, обращаясь только к серверу.
- Подключён тест `scripts/test_culinary_battle_live_client.js`: в браузере подменяется API контролируемыми синтетическими ответами; проверяется отключение деморежима, 26 команд, ошибка неверного кода и закрепление результата. Тест не подменяет облачный E2E и не раздаёт настоящие задания.
- Пользовательский **закрытый комплект 26×19** уже был подготовлен ранее. Действительные 26 кодов и 26 HMAC-хешей заново проверены с существующим `BATTLE_PEPPER`; **не генерировать новые коды**, если эти уже планируется раздать. Публичный Git не должен содержать список кодов, секрет и приватную SQL-загрузку.
- В аккаунте Supabase обнаружена единственная организация «Lider» на Free и два действующих проекта сторонних рабочих систем. Любая дополнительная база должна быть **новым изолированным проектом**, созданным только после выбора пользователем организации и подтверждения цены, если она ненулевая. Запрещено устанавливать схему или Edge Function в два существующих CRM-проекта.
- Для полноценного запуска после согласования проекта: (а) развернуть миграцию 26×19, (б) внести **имеющийся** закрытый seed, (в) настроить `BATTLE_PEPPER` через Supabase Dashboard → Edge Function Secrets (никаких значений секретов в Git, чат или MCP), (г) развернуть Edge Function с `verify_jwt=false`, (д) проверить 26 команд, 19 свободных блюд, 0 результатов, отказ неверного кода, секретность и атомарность последней выдачи, (е) вписать публичный endpoint в meta, (ж) проверить реальный браузер и только затем по разрешению организатора перевести `ready → open`.
- **Не отправлять персональные коды участникам и не открывать мероприятие**, пока этот контроль не закончен. После 19-го результата база автоматически закроет новые выдачи; повторный просмотр сохранится.


**Состояние:** новый режим готовится в отдельной GitHub-ветке. Он НЕ является работающей публичной жеребьёвкой, пока отдельная база Supabase не развернута, секреты не настроены и организатор не открыл событие. Публичная версия `?demo=1` — только локальная имитация.

## Правила, утверждённые организатором 12 ноября 2026 года

- В конкурсе могут принять участие **все 26 ТОСов**, которые указаны в актуальном каталоге `data/toses.json`. Названия и `tos_slug` скопированы в `culinary-battle/demo-data.json` и проверяются тестом на совпадение.
- Доступны **19 блюд**, перечисленных организатором, включая чувашскую **хуплу**. Список зафиксирован в `culinary-battle/demo-data.json` и проверяется тестом.
- Каждый ТОС получает **один индивидуальный секретный код** (26 случайных 24-символьных кодов). Коды передаются лично; в Git их нет, в БД только HMAC-SHA256 с отдельным секретом `BATTLE_PEPPER`.
- Порядок получения блюд — по моменту первого **успешного серверного получения** задания после открытия. При успешном вводе правильного кода сервер случайно выбирает одно из ещё свободных блюд и закрепляет за ТОСом.
- Два ТОСа никогда не должны получить одно блюдо. Не может быть более одной записи на ТОС, более 19 назначений суммарно и более одной записи на блюдо. Это ограничено составным первичным ключом, уникальным индексом и блокировкой строки события в PostgreSQL.
- После выдачи 19-го блюда сервер автоматически переводит мероприятие в `closed`. **Оставшиеся семь ТОСов не получат задания**, даже имея правильный код. Ранее участвовавшие могут посмотреть своё блюдо по своему коду после закрытия.
- Результаты другим ТОСам не видны. Организатор проверяет полный список только через защищённые SQL-инструменты; панель на сайте не нужна.
- Допускается ручное закрытие организатором раньше 19 назначений без автоматического последующего открытия; новые назначения после этого не выдаются.

## Файлы и архитектура

- Публичная страница: `/culinary-battle/`; CSS `assets/css/culinary-battle.css`, JS `assets/js/culinary-battle.js`, стандартные шапка, меню, логотип и темы портала.
- Публичный **деморежим**: `/culinary-battle/?demo=1`; 24 настоящих названия ТОСов и 19 настоящих названий блюд, но фальшивые видимые коды `DEMO-01-2026`…`DEMO-26-2026` и назначения только в localStorage **конкретного браузера**. Результаты учебные и маркируются «ДЕМО». Другой браузер начинает независимую демонстрацию; нет реальной общей очереди. Это нельзя использовать для конкурса.
- База: `supabase/migrations/20261106140000_culinary_battle.sql`. Эта исходная миграция заменяет испорченную предыдущую 18×18; **предполагается, что прежняя миграция нигде не применена**, что необходимо проверить перед запуском. Если она была применена, нужно согласовать отдельный миграционный переход, а не выполнять `create table` поверх живых таблиц.
- Сервер: `supabase/functions/culinary-battle/index.ts`, отдельный Supabase-проект, публичная Edge Function с `verify_jwt=false`, проверкой уникального кода, HMAC, ограничением запросов и RLS/GRANT. В браузер не передаются секреты сервера, назначения других ТОСов или список использованных блюд.
- `GET /functions/v1/culinary-battle?event=culinary-battle-2026` отдаёт `{status,teams,total_teams:26,total_dishes:19,remaining}` — только публичные названия и счётчики.
- `POST /functions/v1/culinary-battle` с `{event,team_id,code}` при правильных данных возвращает только `{team_name,dish_name,revealed_at,first_open,remaining?}` для этого ТОСа; при отсутствии свободных блюд — `{error:'sold_out'}`.
- Серверное назначение выполняет RPC `public.battle_reveal` с `SECURITY INVOKER` и только ролью `service_role`; RLS включена для всех таблиц, доступ `anon/authenticated` отозван.

## Пределы безопасности

CORS/Origin сами по себе не защищают от небраузерных клиентов. Защита основана на длинном индивидуальном коде, серверной проверке HMAC, RLS/GRANT, отказе после окончания блюд и SQL-ограничениях. Перед открытием обеспечить rate limiting на edge/WAF и секретную резервную копию.
