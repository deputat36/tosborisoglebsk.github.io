# Автономный план улучшения портала ТОС БГО

Обновлено: 15 июля 2026 года.

Рабочий репозиторий: `deputat36/tosborisoglebsk.github.io`.
Рабочая ветка: `release-2025-12-22`.

## 1. Текущее состояние

Технический каркас портала, основной генерационный pipeline, контроль SEO, ссылок, доступности, производительности, visual baseline, CSS fingerprint, защита правовых статусов и guardrails публикации уже работают.

Production generation и public deployment smoke подтверждены. Открытой остаётся ручная проверка `Settings → Pages`: source branch, папка публикации, HTTPS enforcement и deployment logs.

Главные риски теперь находятся вне кода:

- официальный состав ТОСов БГО не подтверждён первичным источником;
- полностью проверенных карточек со статусом `verified` нет;
- основания публикации личных сведений по 24 карточкам требуют фактической проверки;
- оператор персональных данных и юридически утверждённая модель обработки данных не определены;
- подготовленные исходящие запросы ещё не отправлены;
- муниципальная правовая база не привязана к подтверждённым действующим официальным актам.

Закрытая issue #165 больше не является открытым блокером. Visual baseline, матрица регрессии и CSS fingerprint введены; любые новые заметные изменения интерфейса по-прежнему требуют отдельного visual comparison.

## 2. Основной принцип

Ассистент продолжает безопасные технические, редакционные и организационные улучшения самостоятельно и не ждёт подтверждения по каждому шагу.

Решение пользователя или внешнего специалиста требуется только там, где без него нельзя достоверно продолжить работу либо есть риск опубликовать спорные сведения, выполнить действие от имени проекта или создать юридически значимый статус.

## 3. Что ассистент делает самостоятельно

- исправляет технические, структурные и навигационные недочёты;
- улучшает служебные страницы и рабочие маршруты;
- создаёт и обновляет CSV, JSON, чек-листы, матрицы, журналы и контрольные страницы;
- поддерживает генераторы, проверки, документацию и GitHub Issues;
- готовит черновики запросов, писем, новостей и карточек;
- усиливает тексты только на основе уже подтверждённых источников;
- фиксирует степень доверия, происхождение контента и ограничения публикации;
- синхронизирует `/github-tasks/`, `data/github_manual_tasks.csv` и очередь решений;
- не меняет неподтверждённые публичные факты ради формального прогресса.

## 4. Когда требуется решение пользователя или внешнее действие

Согласование или фактическое действие требуется, если нужно:

- отправить запрос, письмо или сообщение от имени проекта;
- опубликовать телефон, email, ФИО, фото, логотип или иной материал, где требуется основание публикации;
- изменить председателя, границы, статус, численность или официальный состав ТОС;
- перевести карточку в `partial` или `verified`;
- определить оператора персональных данных и закрытое хранилище доказательств;
- утвердить политику, согласия, порядок исправления, удаления и отзыва;
- подтвердить муниципальные правовые процедуры официальным источником или профильным специалистом;
- менять домен, DNS, GitHub Pages settings или настройки доступа;
- выполнять заметный визуальный редизайн;
- публиковать выводы, которые не подтверждены источником.

## 5. Что запрещено делать без подтверждения

- выдумывать контакты, даты, статусы, председателей, результаты и официальные процедуры;
- считать редакционный материал официальным реестром или юридическим заключением;
- смешивать победу проекта в конкурсе с фактом его реализации;
- публиковать закрытые персональные данные, переписку, подписи и оригиналы согласий;
- использовать фото и логотипы без понятного права на публикацию;
- закрывать GitHub-задачи без фактического результата;
- проставлять фиктивные даты отправки, получения ответа или проверки;
- создавать `source_ref`, `publication_consent_ref`, `decision_ref` или `evidence_ref` без реального основания;
- повышать юридический или фактологический статус автоматически.

## 6. Актуальные этапы работы

### Этап 1. Доверие к четырём приоритетным карточкам

Цель: подготовить Ивановку, Подстёпки, Губари и Танцырей к точечному обновлению без предположений.

Следующие действия:

- найти рабочий канал связи для Ивановки и Подстёпок;
- после отдельного разрешения отправить подготовленные запросы по Губарям и Танцырею;
- фиксировать источник, дату, scope и допустимое основание публикации;
- обновлять `data/toses.json` только после получения доказательств;
- не повышать статус автоматически.

### Этап 2. Исходящие запросы

Цель: перевести 15 подготовленных задач из черновиков в фактическую работу.

Следующие действия:

- использовать `/outreach-register/` как единый журнал;
- отправлять запросы только после реального решения об отправке;
- фиксировать канал, дату, срок повторного контакта и ответственного;
- разбирать ответы через `/reply-review/`;
- не ставить `sent`, `waiting` или `received` без фактического действия.

### Этап 3. Официальный реестр ТОС

Цель: подтвердить полный состав ТОСов БГО первичным источником и только затем расширять каталог.

Следующие действия:

- использовать `/registry-intake/` и `/registry-diff/`;
- хранить кандидатов отдельно от подтверждённого каталога;
- не создавать публичные карточки по слухам и вторичным упоминаниям;
- после получения официального перечня сформировать небольшие проверяемые PR.

### Этап 4. Основания публикации 24 карточек

Цель: для каждой текущей карточки определить безопасный и проверяемый публичный объём сведений.

Следующие действия:

- вести работу по очереди `13 / 9 / 2` из `data/publication_basis_review_queue.csv`;
- использовать подготовленные безопасные шаблоны;
- не считать обычную переписку согласием на распространение данных;
- по результату оставить подтверждённое поле, заменить личный канал общим, удалить поле либо сохранить `needs_review`;
- не загружать сырые ответы и закрытые доказательства в публичный репозиторий.

### Этап 5. Юридическая готовность и персональные данные

Цель: перейти из режима `pre_legal_readiness` к юридически проверенной модели работы.

Следующие действия:

- определить оператора портала и его правовой статус;
- назначить ответственных за закрытое хранение и юридическую проверку;
- выбрать реальное закрытое хранилище доказательств;
- подготовить и проверить политику обработки персональных данных;
- подготовить отдельное согласие на распространение конкретных данных и разрешение на медиа;
- утвердить порядок исправления, удаления и отзыва;
- подтвердить муниципальные процедуры официальными актами.

### Этап 6. Подтверждённый контент

Цель: увеличивать долю материалов, которые можно проверить по источнику.

Следующие действия:

- вести `/content-discovery/`, `/content-intake/` и `/publication-queue/`;
- публиковать новости и результаты только с понятным источником;
- отдельно получить фактический статус реализации проекта ТОС «Миролюбие»;
- не представлять стартовую идею или запрос как выполненный проект.

### Этап 7. Техническая устойчивость

Цель: сохранять стабильность после завершения основных технических P0-этапов.

Следующие действия:

- контролировать `data/site_health.json`, RSS, sitemap и page index;
- поддерживать public deployment smoke и read-only governance-проверки;
- завершить ручную проверку `Settings → Pages` по issue #164;
- не выдавать производный файл за доказательство настройки GitHub Pages;
- сохранять visual baseline и CSS fingerprint при изменениях интерфейса.

## 9. Правило спорных моментов

Если возникает развилка, ассистент обязан:

1. Сформулировать проблему одним предложением.
2. Предложить безопасное решение по умолчанию.
3. Объяснить риск.
4. Запросить только одно необходимое решение.
5. После ответа зафиксировать правило в документации, данных или issue.

## 10. Режим продолжения по умолчанию

Без отдельного запроса ассистент продолжает:

- исправлять технические и структурные недочёты;
- улучшать служебные страницы и рабочие маршруты;
- поддерживать CI, генераторы и governance-контракты;
- создавать черновики и контрольные файлы;
- обновлять документацию и статус проекта;
- усиливать подтверждённый контент;
- искать рассинхронизацию между Issues, CSV, JSON и страницами.

Пользователь требуется только для реальных внешних действий, подтверждений, юридических решений и изменений публичных фактов.
