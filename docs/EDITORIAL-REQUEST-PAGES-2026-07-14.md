# Внутренние страницы подготовки запросов

Дата: 14 июля 2026 года.

## Две внутренние редакционные страницы

Внутренними рабочими страницами считаются:

- `/data-requests/priority-tos/` — подготовка персональных запросов по четырём приоритетным карточкам;
- `/data-requests/tos-registry-request/` — подготовка запроса актуального реестра ТОС БГО.

Обе страницы содержат полезные шаблоны и внутренние ссылки, но не являются самостоятельными публичными материалами портала.

## Индексация

Для обеих страниц используется `noindex,follow`.

Это означает:

- поисковику не предлагается показывать страницу как отдельный публичный материал;
- внутренние ссылки на карточки, трекеры, методики и публичную форму передачи данных остаются доступными для обхода;
- страницы не входят в sitemap;
- canonical остаётся собственным, чтобы URL не маскировался под другую страницу.

`nofollow` здесь не используется, потому что страница связывает рабочий процесс с поддерживаемыми маршрутами сайта.

## Статус действий

Готовый текст не означает факт отправки запроса.

Отдельно различаются:

1. текст подготовлен;
2. канал связи найден;
3. запрос отправлен вручную;
4. ответ получен;
5. ответ разобран;
6. сведения подтверждены;
7. карточка или реестр обновлены.

Страница не содержит активной формы, сетевого вызова или автоматической отправки. Факт отправки должен подтверждаться рабочим трекером и внешним evidence.

## Публичный маршрут остаётся доступным

Ограничение индексации внутренних шаблонов не скрывает публичную форму передачи данных.

Житель, председатель или партнёр может использовать `/update-tos/`, чтобы подготовить сообщение и передать открытые сведения. Внутренние страницы нужны редактору для контроля процесса и не заменяют этот публичный маршрут.

## Персональные данные

Шаблоны могут содержать уже опубликованные ФИО, email или ссылки на открытые сообщества, необходимые для подготовки обращения.

Это не даёт права:

- публиковать новый личный контакт без согласия или открытого основания;
- переносить закрытую переписку в публичный репозиторий;
- считать контакт подтверждённым только потому, что он присутствует в шаблоне;
- переводить карточку в `verified` без источника и проверки.

## Автоматическая защита

`scripts/audit_editorial_request_pages.js` проверяет:

- ровно один robots meta `noindex,follow` на каждой странице;
- правильный canonical;
- явное описание редакционной роли;
- честный статус «подготовлено, но не отправлено»;
- отсутствие активной формы и автоматической сетевой отправки;
- наличие маршрутов к трекерам, методике и `/update-tos/`;
- отсутствие обоих URL в sitemap;
- подключение проверки к package и обоим project-mode audits.

## Публикация

На pull request sitemap регенерируется во временном рабочем каталоге CI, а commit generated files пропускается.

После слияния push-workflow должен регенерировать sitemap и page index основной ветки. Затем отдельно проверяются push-run, generated commit, Pages deployment и фактическое отсутствие внутренних URL в опубликованном sitemap.
