# Аудит локальной админ-панели ТОС БГО

Дата: 13 июля 2026 года.

## Краткий вывод

Админ-панель покрывает большую часть первоначального issue №8: редактирование девяти основных наборов данных, dashboard, поиск, фильтры, локальные черновики, автозаполнение, проверку качества, preview и экспорт.

Главной проблемой была не нехватка кнопок, а накопление экспериментальных дублей и неполная синхронизация с публичными коллекциями. Основная страница одновременно подключала два одинаковых модуля логотипов, отдельная HTML-копия подключала ещё три варианта массового автозаполнения, а `data/done.json` не был доступен в редакторе.

После аудита оставлена одна поддерживаемая страница `/admin/` и шесть модулей:

- `admin/admin2.js` — редактор и базовая логика восьми исходных разделов;
- `admin/admin-done-dataset.js` — схема раздела «Результаты» для `data/done.json`;
- `admin/admin-logo-tools.js` — массовые пути логотипов, no-logo фильтр и CSV;
- `admin/admin-dashboard.js` — обзор и аналитика девяти коллекций;
- `admin/admin-export-tools.js` — CSV текущей отфильтрованной выборки;
- `admin/admin-history.js` — локальные снимки и восстановление.

Фактический реестр возможностей: `data/admin_capability_inventory.csv`.

## Реализованные возможности

### Dashboard

Dashboard собирает данные из JSON или локальных черновиков и показывает:

- количество ТОСов;
- отсутствие телефонов, логотипов и соцсетей;
- черновики новостей;
- ближайшие и прошедшие события;
- проекты без привязки к ТОС;
- количество результатов и записи, которым не хватает подтверждающего источника;
- потребности без контакта;
- документы без ссылки;
- количество привязанных проектов, результатов, событий и потребностей;
- CSV председателей.

### Редактор

Поддерживаются девять коллекций:

- каталог ТОС — `data/toses.json`;
- новости — `data/news.json`;
- материалы — `data/articles.json`;
- документы — `data/documents.json`;
- конкурсы — `data/grants.json`;
- проекты — `data/projects.json`;
- результаты — `data/done.json`;
- календарь — `data/events.json`;
- потребности — `data/needs.json`.

Для каждого раздела доступны создание, редактирование, дублирование, удаление, импорт JSON и скачивание JSON.

Схема результатов отдельно фиксирует:

- дату и привязку к ТОС;
- что было до;
- что сделано;
- подтверждённый результат;
- участников;
- название и URL источника;
- каких подтверждений не хватает;
- происхождение материала `verified`, `editorial`, `starter` или `request`.

Это не повышает статус результата автоматически: публикация без источника или с незакрытым `needs_details` остаётся заметной в dashboard и проходит репозиторные проверки доверия.

### Поиск, фильтры и качество

Доступны:

- полнотекстовый поиск по записи;
- published / draft;
- заполненность ниже 70%;
- записи с привязкой к ТОС;
- ТОС без логотипа;
- дубли slug или id;
- неизвестный `tos_slug`;
- оценка заполненности;
- предупреждение о нестандартном пути логотипа;
- отдельная dashboard-индикация результатов без источника или с запросом подтверждений.

Браузерная проверка не подтверждает фактическое существование каждого файла и актуальность внешней ссылки. Эту задачу продолжают выполнять репозиторные CI-аудиты.

### Автозаполнение

Для одной записи и массово для каталога ТОС заполняются только отсутствующие значения:

- `slug` из названия;
- `updated_at` текущей датой;
- рекомендуемый путь `/assets/img/tos-logos/<slug>.svg`.

Автозаполнение пути не означает, что SVG существует или разрешён к публикации.

### Черновики и откат

Основной редактор сохраняет текущие данные в `localStorage`.

Модуль `admin/admin-history.js`:

- создаёт ручной снимок раздела;
- автоматически создаёт снимок перед импортом, добавлением, удалением, дублированием и автозаполнением;
- хранит до десяти снимков на раздел;
- восстанавливает последний снимок;
- перед восстановлением сохраняет текущее состояние как резервный снимок.

Локальные снимки не заменяют скачиваемый общий JSON-backup, потому что привязаны к конкретному браузеру и устройству.

### Экспорт

Поддерживаются:

- JSON текущего раздела;
- общий JSON-backup всех девяти разделов;
- CSV председателей;
- CSV ТОСов без логотипа;
- CSV текущей отфильтрованной выборки любого раздела.

## Намеренно исключённые функции

### Прямой commit/push в GitHub

Клиентская админка размещена на GitHub Pages. Хранение GitHub token в JavaScript, HTML, localStorage или пользовательской форме создало бы риск раскрытия доступа к репозиторию.

Поэтому админка:

- не обращается к GitHub API;
- не хранит токены;
- не делает commit и push;
- скачивает подготовленный JSON;
- передаёт публикацию в обычный GitHub workflow с CI-проверками.

Прямую публикацию можно рассматривать только после появления отдельного защищённого backend, авторизации, журналирования и ограниченных прав.

### Drag-and-drop загрузка логотипа

Статическая страница может локально прочитать файл и показать preview, но не может безопасно записать его в репозиторий. Текущая админка формирует правильное имя и CSV очереди, а сам SVG загружается через GitHub.

### Автоматическая генерация текстов

Генерация фактических карточек и новостей без источников противоречит текущему P0-режиму доверия. Возможный будущий генератор должен:

- создавать только черновик;
- хранить происхождение текста;
- не придумывать контакты, даты и результаты;
- требовать ручного подтверждения;
- проходить проверку персональных данных.

До этого используются `/update-tos/` и `/communication-kit/`.

## Блокирующие проверки

- `scripts/audit_admin_capabilities.js` проверяет поддерживаемые модули, реестр возможностей, evidence-пути и отсутствие клиентских токенов/API-записи;
- `scripts/audit_admin_dataset_schema.js` сопоставляет девять разделов админки с реальными `data/*.json`, ключевыми полями и связями `tos_slug`;
- `check:js` проверяет синтаксис папки `admin/`;
- обычный и полный project-mode audit включают обе проверки.

## Следующий безопасный этап

1. Не расширять прямую публикацию до появления защищённого backend.
2. При изменении схем JSON обновлять `DATASETS`, dashboard, реестр возможностей и schema-аудит одновременно.
3. Расширять проверки внешних URL и файлов только на уровне Node.js CI, а не выдавать браузерную эвристику за подтверждённый факт.
4. Не переводить результаты в подтверждённые без источника, даты и закрытого `needs_details`.
